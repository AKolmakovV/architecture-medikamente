## Диаграммы потоков данных (Data Flow Diagrams)

Жирным цветом выделены движение данных.

### **Регистрация пациента в клинике**

![Регистрация пациента](./Data%20Flow%20Diagrams/as-is/Регистрация%20пациента.png)

**Поток данных**

1. Пациент первый раз обращается в клинику, и просит записать его на прием (данные: ФИО)
2. **Администратор скачивает файл Patiens и ищет информацию о пациенте (ФИО/Страховка/Телефон)**
3. Не обнаружив данную информацию, администратор понимает что пациент не зарегистрирован и предлагает пройти процедуру регистрации
4. В случае согласия, администратор запрашивает личные данные (ФИО, Паспортные данные, Информацию о болезнях и противпоказания, ...), достаточные для регистрации пациента и создания карточки пациента 
5. Администратор заполняет файлы Patiens данными о пациенте
6. Администратор создает и заполняет файл карточки пациента
7. **Администратор загружает заполненный файл Patiens на общий диск**
8. **Администратор загружает заполненный файл "Карточка пациента" на общий диск**

### **Запись пациента на прием**

![Запись пациента на прием](./Data%20Flow%20Diagrams/as-is/Запись%20пациента%20на%20прием.png)

**Поток данных**

1. Пациент обращается в клинику, и просит записать его на прием (данные: ФИО, Дата рождения) (ранее пациент уже был зарегистрирован)
2. **Администратор скачивает файл Patiens и ищет информацию о пациенте (ФИО/Страховка/Телефон/...)**
3. Проверка наличия клиента в Excel файле Patiens, а также необходимых атрибутов 
4. **Администратор скачивает файл - Журнал приема пациентов**
5. Администратор вносит записи о предстоящем посещении в свободный слот у варача в файл "Журнал приема пациентов"
6. Администратор вносит записи о предстоящем визите в файл "Учёт пациентов и платежей (Patiens)"
7. **Администратор загружает файл "Журнал приема пациентов" на общий диск**
8. **Администратор загружает файл "Учёт пациентов и платежей (Patiens)" на общий диск**


### **Прием пациента у врача**

![Прием пациента у врача](./Data%20Flow%20Diagrams/as-is/Прием%20пациента%20у%20врача.png)

**Поток данных**

1. **Врач скачивает "Журнал приема пациентов" и ожидает пациента указанного в журнале**
2. Пациент приходит на прием
3. **Врач скачивает Excel файл "Карточка пациента" с данными нужного пациента**
4. **Врач проверяет, какие анализы есть на пациента, для этого он ищет и скачивает файлы анализов с данными нужного пациента**
5. Врач выслушивает пациента/собирает анамнез/выполняет необходимые процедуры и вносит необходимую информацию (диагноз) в файл "Карточка пациента"
6. **Прием окончен, врач загружает файл "Карточка пациента" на общий диск**

### **Оплата пациентом полученных услуг**

![Оплата пациентом полученных услуг](./Data%20Flow%20Diagrams/as-is/Оплата%20пациентом%20полученных%20услуг.png)

**Поток данных**

1. **Пациент приходит на кассу для оплаты услуг, кассир скачивает с общего диска Excel файл "Журнал учета пациентов и оплаты"**
2. Кассир видит, услуги и стоимость и вводит данные в кассовый аппарат (ККМ)
3. **После выполнения оплаты, ККМ отправляет соответствующую информацию в систему 1С Бухгалтерия предприятия**
4. Пациенту выдается чек, кассир вносит информацию об оплате в файл "Журнал учета пациентов и оплаты"
5. **Кассир загружает файл "Журнал учета пациентов и оплаты" на общий диск**

## Проведите аудит мер по обеспечению безопасности данных

1. Файлы находятся в доступности всех сотрудников, даже тем кому не должны - чем больше доступность, темы выше риск компрометации (нарушение 152-ФЗ)
2. Файлы не зашифрованы, хранятся как есть - в случае утечки данных, ими свободно могут воспользоваться (нарушение 152-ФЗ)
3. Сотрудникам доступна избыточная информация о пациентах, избыточная в контексте выполнения их обязанностей (например кассир скачивает файл учета пациентов и платежей, не должен получить доступ к информации о месе работы или учёбы, прописке) (нарушение 152-ФЗ Статья 5)
4. Нет контроля за данными, их изменением, ровно как и нет никакого аудита в принципе (нарушение 152-ФЗ)
5. Каналы передачи файлов не защищены, существует риск перехвата (нарушение 152-ФЗ)
6. Данные дублируются в разных файлах, из за этого снижается контроль за данными и усложняется процедура их защиты (нарушение 152-ФЗ)
7. Нет ни ABAC ни RBAC достум к данным имеет любой сотрудник (нарушение 152-ФЗ)
8. Администраторы не запрашивают и не получают согласие на обработку персональны данных (нарушение 152-ФЗ)

Общее заключение: Нарушаются правила и требования обозначенные в "Федеральном законе о персональных данных (152-ФЗ)"

### Рекомендация по тегированию данных

Для всех видов данных применить:
1. Шифрование (хранение\передача)
2. Маскирование
3. Разделение доступности RBAC/ABAC

Применяемые теги:
1. Персональные данные - PII
2. Медицинские данные - PHI
3. Платежные данные - FIN
4. Внутренние данные (прим.инвентаризация и мат.ценности) - Internal

Инструменты:

1. BitLocker (шифрование дисков) + Шифрование SMB/AD RMS (если требуется обмен файлами по сети) - Шифрование (хранение\передача)
2. В перспективе PostgreSQL (+SSL/TLS, pgcrypto) - Шифрование (хранение\передача)
3. Макскирование тоже на перспективу будем использовать PostgreSQL Anonymizer
4. Для тегирования даннх использовать PostgreSQL pg_tags
5. Групповые политики Active Directory - Разделение доступности RBAC/ABAC
6. Журнал событий и ошибок Windows
7. DLP (например "Solar Dozor")
8. Keycloak пригодится на стадии разработки нового решения (+2FA)
9. Внедрение SIEM (например "Kaspersky KUMA")
10. При разработке для решений Frontend использовать обфускация кода

## TO-BE Диаграммы потоков данных (Data Flow Diagrams)


Жирным цветом выделены движение данных.
Все соединения между системами используют шифрование минимиум TLS 1.2

### **Регистрация пациента в клинике**

![Регистрация пациента](./Data%20Flow%20Diagrams/to-be/Регистрация%20пациента.png)

**Поток данных**

1. Пациент первый раз обращается в клинику, и просит записать его на прием (данные: ФИО)
2. Администратор запрашивает разрешение на обработку персональных данных
3. **Администратор открывает форму для ввода данных нового пациента и заполняет (ФИО/Страховка/Телефон)**
4. **Автоматически предлагается заполнить отдельную форму - карточка пациента**
5. **После проверки заполненных данных, администратор нажимает на кнопку - сохранить, и данные поступают в CRM систему, для дальнейшего хранения и обработки**
6. **Веб приложение передает имеющиеся данные в сервис CRM системы**
7. Данные валидируются  (безопасность\уникальность)
8. **Данные записываются в базу данных сервиса CRM**
9. База данных шифрует данные

### **Запись пациента на прием**

![Запись пациента на прием](./Data%20Flow%20Diagrams/to-be/Запись%20пациента%20на%20прием.png)

**Поток данных**

1. Пациент обращается в клинику, и просит записать его на прием (данные: ФИО, Дата рождения) (ранее пациент уже был зарегистрирован)
2. **Администратор открывает страницу с журналом приема пациентов по нужному врачу**
3. Администратор вносит записи о предстоящем посещении в свободный слот у варача
4. **Данные сохраняются - информация о записи передается от WEB приложения в сервис CRM (Ф.И.О. Врача и Пациента, Дата и время визита)**
6. **Сервис CRM сохраняет данные базу данных, данные в последствии шифруются**


### **Прием пациента у врача**

![Прием пациента у врача](./Data%20Flow%20Diagrams/to-be/Прием%20пациента%20у%20врача.png)

**Поток данных**

1. **Врач открывает страницу веб приложения - "журнал пациентов" где видит информацию только по "своим" пациентам**
2. **Врач готовится к приему пациента согласно журналу пациентов, он открывает карточку пациента (карточка пациента уже содержит данные анализов если есть)**
3. Врач выслушивает пациента/собирает анамнез/выполняет необходимые процедуры и вносит необходимую информацию (диагноз) в веб приложении, в интерфейсе "Карточка пациента"
6. **Прием окончен, врач сохраняет изменения в карточке пациента, данные отправляются сервису CRM, далее в базу данных, с последующим шифрованием**

Важно! 

1. Врач имеет доступ и видит данные только по "своим" пациентам
2. Карточка пациента позволяет просмотреть старые данные (без изменения) или внести новые записи

### **Оплата пациентом полученных услуг**

![Оплата пациентом полученных услуг](./Data%20Flow%20Diagrams/to-be/Оплата%20пациентом%20полученных%20услуг.png)

**Поток данных**

1. **Пациент приходит на кассу для оплаты услуг, кассир открывает страницу услуг по пациенту, отображаются только не оплаченные услуги, название услуги маскируется**
2. Кассир выбирает нужную услугу, и выбирает ее для проведения оплаты
3. Кассир видит стоимость и вводит данные в кассовый аппарат (ККМ)
4. **После выполнения оплаты, ККМ отправляет соответствующую информацию в сервис CRM системы**
5. **Сервис CRM системы меняет статус активной услуги для пациента на оплачено, изменения проводятся в базе данных сервиса**
6. **Данные по оплате CRM сервис отправляет в 1С Бухгалтерию с использованием REST  HTTPS/TLS 1.2**
